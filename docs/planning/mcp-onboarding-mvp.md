# Reliable MCP onboarding — bounded local MVP

**Status:** proposed execution plan; owner discussion before implementation.  
**Date:** 13 October 2026. **Source:** staging `26e90126a1987b1dc6e689438b471fe5ed932235`.  
**Owner intent:** make existing open-source MCP servers straightforward to connect and use. Keep the local MVP small; investigate and obtain independent critique before agreeing implementation.

## Briefing and stopping point

Build on the existing MCP settings screen: import a supported configuration, review what it will run or contact, save credentials safely, test the connection, assign the server to an agent, then use an eligible tool in chat under existing permissions. A successful import alone is not success. Completion means this entire journey works after restart, with meaningful failure messages and independently verified approval/denial effects.

Recommend **preinstalled stdio servers and Streamable HTTP endpoints**, including static environment/header credentials. This is a connection workflow, not a universal package installer. Users retain responsibility for choosing trusted servers and installing their runtime in the execution environment. Local processes run with the API host's authority; tool approval does not sandbox a server or prevent effects during its startup. The UI must make this clear before testing or enabling use.

No new account, subscription, database, SDK major upgrade or external dashboard is required. Existing TypeScript, SQLite, encrypted secret storage and MCP SDK are sufficient. Estimate **5–7 focused engineering days**, including connected tests and review, plus variable hosted CI time. This is a planning estimate, not a deadline. Reassess after the connection/credential slice; if the remaining work cannot fit seven days, bring a reduced proposal rather than expanding silently.

## Requirements and design boundaries

- **MCP-01 — One configuration contract.** Accept bare endpoint URL, one command configuration, named map and `mcpServers` wrapper. Validate every entry before save; show per-entry errors and explicit selection, with no silent partial batch import. A selected batch saves transactionally. Canonical new transport values are `stdio` and `streamable-http`. Read legacy `http` as Streamable HTTP. Preserve existing `sse` records as a clearly labelled legacy alias to their existing Streamable HTTP behavior; do not claim real SSE support or rewrite stored records without an explicit save. Unknown transport/configuration fields receive an actionable unsupported message rather than being silently ignored. Explicitly list accepted fields in the shared schema; environment interpolation such as `${VAR}`, shell strings and custom cwd are unsupported in this slice and must not be silently expanded or discarded.
- **MCP-02 — Explicit host and trust.** Import/save never spawn a process or contact the endpoint. Test and agent assignment disclose that future chat requests may launch/contact this trusted server. Stdio uses an executable and argument array, no added shell wrapper. It uses the API execution host: Docker container for web/Compose, native backend host for Electron. A Mac binary path does not exist inside Docker. Missing runtime/executable gets guidance; no installer, automatic download, package manager invocation or privilege escalation is added. User-supplied commands can themselves download or execute code; disclose this and use preinstalled pinned fixtures for acceptance.
- **MCP-03 — Credentials with one resolver.** Encrypt all supplied env/header values through the existing secret store, retaining names and server-owned references separately from the public response. API returns names and configured flags only. Writes distinguish retain, replace and clear. Clients cannot supply arbitrary secret references. Duplicate omits credentials and clearly requires re-entry; delete removes only that server's owned secrets. Test and chat use the same validated resolver. Decrypt only at connection time; do not forward the whole API environment. Explicit env names must be valid and must reject process injection/reserved names (`NODE_OPTIONS`, `NODE_PATH`, `LD_*`, `DYLD_*`, `SECRETS_MASTER_KEY`); preserve the SDK's documented minimal inherited environment. All credential values, including non-secret-looking env values, use the same encrypted storage rule.
- **MCP-04 — Existing data and transport safety.** Public reads immediately mask legacy env/header values. Before activation, migrate legacy plaintext values in one DB transaction: encrypt and replace their metadata with owned references; rollback on any error. Missing/invalid master key blocks credential writes and activation, retaining existing data without returning plaintext. Uncredentialed servers still work. A structurally valid key cannot be proved historically correct using plaintext alone: wrong-key tests use existing authenticated ciphertext and must fail decryption before connection. Public reads/copy/errors/reports must also strip legacy URL userinfo, query and fragment values and show a needs-reconfiguration flag. Such records cannot connect until explicitly replaced with an allowed endpoint and encrypted credentials; failed replacement preserves stored data without exposing it. Existing DB files/backups may retain historical bytes; no secure-erasure claim. Do not recursively accept arbitrary metadata as connection options. For HTTP accept HTTPS and explicitly entered local HTTP endpoints (`localhost`, loopback IPs, `host.docker.internal`); reject other cleartext HTTP, URL userinfo/fragments/query credentials and all redirects. Query strings are excluded in this MVP to avoid ambiguous credential leakage. Reject invalid headers, CR/LF, Host, Cookie and transport-managed protocol/session/content headers. Static Authorization and service-specific API-key headers are allowed. No OAuth or browser sign-in; return clear authentication guidance. This is a trusted endpoint configuration boundary, not a general SSRF/DNS-rebinding sandbox. Preserve the separate existing system-tool URL guard.
- **MCP-05 — Understand test results.** Show handshake/discovery outcome, discovered count, eligible count and safe rejection categories. Reuse the same trust filter as chat; do not relax shadow-tool/schema/injection checks. Test never invokes a tool. Record test time and configuration revision; invalidate success after edits. Unsupported/oversized catalogs remain explicit errors or existing context-budget refusals, not a new gateway-selection framework. Display safe stage/code/retry guidance for missing executable, invalid config, authentication, timeout and server crash. Discard raw server stderr, response bodies and exception causes from user reports/logs; bounded internal status metadata is sufficient. Do not promise arbitrary malicious-server output cannot contain secrets; these are trusted servers, and tool-result content still follows existing output controls.
- **MCP-06 — Assignment and real tool use.** Only assigned, eligible tools enter model context. Preserve Ask/Allow/Block, approval resume and unassigned/rejected denial. Test success does not grant tool permission. Use namespaced IDs, current tool/schema admission and existing output/context controls. Save/assign/restart must preserve config and secret ownership. Edits/unassign/delete affect new requests; an in-flight request may settle using its existing snapshot. Waiting approval is not an already-executing snapshot: bind each pending MCP approval to the server ID, server configuration revision (incremented on endpoint, command, args, env/header or credential change), and canonical selected-tool schema revision. Never hash plaintext credentials into public identity. On resume, compare current configuration/assignment/eligible schema before dispatch; any change, missing legacy binding or deletion rejects the stale approval without a tool call and requires a fresh request and permission decision. No claim of immediate revocation or hard cancellation of remote effects already begun.
- **MCP-07 — Bounded lifecycle and diagnostics.** Keep current default connect timeout 20 seconds and request timeout 60 seconds with existing overrides. Close test transports on success/failure, close chat-owned transports on completion/cancel/disconnect. Do not automatically replay `tools/call` after ambiguous failure or reconnect. Distinguish a definitely-unstarted error from an ambiguous post-dispatch failure. An ambiguous outcome terminates automatic reasoning for that turn with a safe unknown-outcome status: do not let the model issue another call, reconnect or replay. A fresh user request is required before any new action, with normal permission checks; the UI tells the user to inspect the possible earlier effect first. This is scoped MCP failure handling, not a general retry engine. Report interrupted/unknown outcomes honestly. Direct fixture processes must terminate; SDK close is not proof of killing arbitrary descendants. Reuse V1 request/run/tool diagnostics for timing, safe failure stage and IDs; no credentials, command arguments or endpoint query in diagnostic exports. Inspect actual reports during E2E and record missing signals without building a new observability platform.
- **MCP-08 — Demonstrate compatibility and regressions.** Execute the connected verification map with real API, SQLite and MCP transport/effects. Add one pinned upstream reference-server smoke journey and disclose its scope. Preserve model configuration, ordinary chat, context budgeting, system-tool permissions and unrelated agent settings.
