# Harness implementation proposal for joint review

Version 2, 13 September 2026 — incorporates owner decisions from voice review. Planning deliverable only. The identifiers below are proposal labels, not created Beads IDs. No implementation, package installation, paid model experiments, Beads edits or reset was performed. This proposal supersedes the sequencing in initial-resolution-plan.md; prior research remains supporting evidence.

## Recommended scope

Propose an initial tranche that decides SDK modernization and framework order before dependent implementation, then makes the selected runtime observable. The owner has not approved this tranche or implementation. Keep TypeScript, existing application services and security, local SQLite and Beads project tracking. Assess a recent stable, supported, mutually compatible dependency set; neither the installed AI SDK nor the newest release is the automatic target. Compare upgrading the existing runtime with adopting supported LangChain providers/middleware. Avoid upgrading an SDK that the chosen framework would immediately replace. Application-specific OpenTelemetry spans remain useful in either path, alongside supported native instrumentation and optional local Phoenix.

Confirmed owner decision: the first local release uses connected local execution with explicit recovery after interruption. Independent execution while the application is closed is deferred. No unattended worker/server deployment is needed for this tranche. Recovery and independent background scheduling remain distinct; local authorization and truthful status still apply. This confirms execution scope only, not approval of the full tranche.

## Schedule and parallel work

Total of all proposed work: approximately 41.5–81 person-days before any re-estimation. This is an effort envelope for the complete proposed scope, not a calendar promise or the price of merely adding Phoenix. With two effective implementation lanes, shared contracts, review and integration prevent a simple divide-by-two schedule.

Recommend reviewing the initial tranche in two gates: first E2 plus framework-independent visibility preparation (V1/V3 and V4 fixtures); then the selected R1 modernization and dependent V2/V4/V5 integration. The complete initial outcome therefore includes E1+E2+R1: 15.5–32 person-days, with R1 counted once in the full-program total. This replaces the earlier E1+E2-only estimate, which omitted modernization needed before dependent tracing. The earlier 2–4-week forecast is withdrawn; a provisional 3–6 working-week window with two effective lanes is a planning envelope only, pending F3, feature completion, credentials and review availability. F3 must produce a revised scheduled estimate before dependent implementation is authorized.

V1+V3 provide 2–4 person-days of independent contract/dashboard preparation, not a complete agent trace. Actual model/tool visibility needs F0→F1→F2→F3→R1→V2; this prevents early instrumentation becoming avoidable legacy work. Narrow existing-boundary instrumentation may be used within a bounded comparison only if reusable or explicitly disposable, not as the default delivery plan.

Principal runtime dependency chain (not a calculated critical path): F0→F1→F2→F3→R1→R2→R3→R5→D1→D2→B2. R4 joins R5 and K3. Knowledge/context and UI join D1/D2 and may determine completion; calculate the actual critical path after task scheduling and staffing. K1→K2 can run alongside F/R work; K3 waits for runtime/cost integration, K4 joins UI. V1/V3 and UI fixtures are independent; V2 and final live UI integration depend on the selected modernization. Knowledge loaders may also share the selected LangChain dependency cohort: source-policy/schema design can proceed early, but package-dependent integration follows F3. Backend and frontend workers can develop V4 against fixtures, but final UI acceptance requires real runtime events. Assign shared contracts/chat routes to one integration owner.

## Oversight and parent-agent operation

Before creating issues, review this package with the owner. Then reconcile existing Beads records and create only approved missing scopes. Use the governed broker when a workflow run is active; retain IDs and original evidence. Draft labels in this document are not live status tracking.

Each actual issue will carry objective/non-goals, allowed paths, acceptance, dependencies, assignee, evidence references and a bounded review gate. Exact branch/authority contracts are created from the accepted baseline when work is authorized; this research proposal does not invent or grant those permissions.

The parent maintains the scheduled dependency graph, owns shared interface integration, verifies specialist evidence, and reports milestone completion, changed estimates and owner decisions. If an experiment consumes its approved budget without resolving the question, deliver its evidence and a smaller recommendation rather than silently expand the experiment. Research-only findings are never reported as runtime passes. Formal execution-contract and repository quality gates apply during implementation.
