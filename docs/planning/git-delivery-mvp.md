## Owner brief and stopping point

A user can review selected files, commit, publish/push and create a GitHub pull request either through the existing panel or by asking the existing Project Chat agent. Both surfaces use the same operations and show accurate results. The user may hide the side panel and keep approvals, results and errors in chat. The preference survives restart.

Stop when both paths complete the same disposable-project journey, required negative cases and diagnostics pass, and the user can understand what happened without opening the panel. This is a local single-user feature. No new CLI, voice implementation, dashboard, automatic merge, branch cleanup, conflict-resolution expansion, force push, rebase, reset, repository creation, account setup or paused orchestration work. Existing wider Git capabilities remain intact but are not added to the chat mutation surface.

Owner accepted these first-slice choices with the plan: whole-file selection rather than line staging; explicit reviewed commit text rather than a new AI-message-generation service; one approval per chat mutation rather than a blanket multi-step authorization. The earlier discussion established chat parity and panel visibility; these defaults are now accepted as part of the plan.

## Proposed technical design

Retain TypeScript, existing contracts, SQLite, React/Next.js and Electron. No new third-party services/accounts/subscriptions. Git and gh already underpin the panel; external authentication stays with the user's existing installation and is never exposed to the model. Missing tools/auth produce actionable unavailable results. No automatic installation or credential harvesting.

Extract a small application-level Git delivery service from the route-local handlers. Both HTTP panel routes and the Project Chat native executor call it. Inject a typed `GitDeliveryPort` into `createSystemToolExecutor`; the harness must not import API modules or own GitHub credentials. Keep read tools and existing external read responsiveness. Do not route writes through generic shell text or the paused `packages/workflow-control` brokers.

Proposed agent operations are selected-file stage/unstage, commit, publish/push and create PR, with fixed enums and no arbitrary executable, shell, environment, flags, root, repository URL or project ID supplied by the model. Resolve the actual Project from persisted session ownership and approved workspace binding on initial execution and resume. Validate readonly/onboarding policies before exposing tools and again in the executor. Add new tools to write/path/risk classifications; use existing high-risk approval handling, never weaken an explicit deny or existing bash policy. Personal Chat has no implicit active-Project mutation access.

### Permission contract

Use the existing execution-policy categories from `packages/contracts/src/settings.ts`; write-tool classification alone is insufficient. The same service gate applies to HTTP panel requests and injected chat executors.

| Operation                            | Required categories                        | Human confirmation                                                                         |
| ------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Stage/unstage selected files; commit | `workspaceWrite`, `gitMutation`            | Exact material confirmation in panel; one persisted approval per chat mutation             |
| Publish/push; create PR              | `workspaceWrite`, `gitMutation`, `network` | Exact destination/material confirmation in panel; one persisted approval per chat mutation |

For every applicable category, `block` wins over `ask` and `auto`, including a later policy change after preparation. No approval overrides a block. `ask` requires the corresponding reviewed confirmation; `auto` does not remove this MVP's stricter per-mutation confirmation. A panel action counts only when it submits the server-prepared reviewed operation, not merely because it comes from HTTP. Resolve current settings and trusted Project capabilities at preparation, immediately before execution, on approval resume and on direct executor/HTTP entry; denied/read-only/path restrictions win. Recheck after taking the repository lock. Deny changed policies without effects and require new preparation when appropriate. Repository hooks remain part of trusted Git execution, not a network sandbox; this classification does not claim to constrain arbitrary existing hook traffic.

### Exact effects and approvals

The service prepares canonical operation material from trusted repository state before presenting a panel confirmation or persisting a chat approval. Material includes full project/repository identity, branch/full HEAD, action arguments, selected literal paths and their content/index fingerprint for staging, entire index tree fingerprint for commit, destination remote/ref and expected local tip for push, and exact repository/head/base/title/body/draft for PR creation. Server-generated material is stored, not trusted merely because the model echoes a hash. Revalidate under a per-repository mutation lock immediately before execution. Changed material yields a clear stale-review result requiring a fresh request/approval; do not silently approve new content.

Panel clicks remain explicit user requests with previews/confirmation; chat writes each require their own visible approval. Existing atomic resume claim prevents duplicate approval consumption. Preserve external `.git` hooks and policies; hook failure reports failure and leaves work intact. Hooks execute repository code through the already trusted Project/Git route; this is not a new sandbox guarantee. Reject mutations to protected integration branches `main`, `master`, `staging` in this bounded flow, detached/unborn HEAD, conflicts and unsupported repository layouts; tell the user to select an existing working branch. No implicit branch creation or policy relaxation.

Selected-file staging uses Git literal pathspec semantics, not just `--`; reject absolute/escaping/.git paths and verify real Project boundary. Cover rename/deletion and unusual valid filenames. Commit preview enumerates the entire actual index: pre-staged unrelated changes must be disclosed and explicitly selected/confirmed or the commit is blocked for the user to resolve. Do not silently unstage or discard them. Concurrent external Git changes fail the expected-state check; never claim locking prevents external processes. Recheck resulting commit tree/parent against approved index/HEAD; surface any mismatch as a failure requiring investigation, not automatic rollback.

### Bounded execution and recovery

Use fixed executable argument vectors and a mutation-specific asynchronous executor, not d185's read-only result semantics. Proposed initial command deadline is the existing mutation maximum 120 seconds, bounded stdout/stderr 2 MiB, and one active mutation per repository; terminate/join owned child processes on cancel/timeout and preserve explicit uncertain outcomes. Hooks must be included in that deadline. No arbitrary timeout increases or automatic mutation retry.

Use a small persisted operation receipt keyed by server-issued operation ID, actor/session and Project; panel retries reuse their ID, chat call IDs map to it. Record expected-state fingerprint and states prepared/executing/succeeded/failed/unknown/cancelled/denied/stale/expired, plus safe returned commit/ref/PR identities. Existing approval records hold reviewed payloads; receipts complement them for mutation result/replay, not a new job scheduler. Store no credentials, prompts or file bodies in receipts. Unique claim and per-repository serialization cover simultaneous panel/chat requests. Retained completed repeats return the same recorded result; mismatched payload/actor/project is rejected.

An unexecuted preparation expires after 15 minutes, including its pending approval. Explicit cancellation/denial or a stale-state rejection closes it immediately with the corresponding effect-free state. Expiry is checked on every read/execute/resume and at startup, with opportunistic cleanup; no scheduler is needed. Once execution has been claimed, expiry must not convert it to an effect-free state. `failed` is reserved for a verified no-effect failure; timeout, disconnect or crash after a possible effect is `unknown`, not failed. A successful effect remains successful if later status enrichment fails, with a refresh warning. User cancellation never implies rollback.

On restart, executing becomes unknown and cannot run again automatically. Reconcile commit by full HEAD/tree/parent, push by actual remote ref, and PR by exact repo/head/base lookup; only return succeeded when the observed effect is uniquely consistent with the receipt. Stage outcomes compare intended and actual index. Ambiguous results stay “outcome unknown—inspect before retry”. No promise of distributed exactly-once GitHub writes. A new equivalent Project/action is blocked while an unacknowledged unknown remains. The user can inspect safe expected/observed state and explicitly acknowledge the ambiguity using a human-only panel/chat control. Record that disposition without changing the unknown outcome to success or permitting automatic replay. This releases the block only for a separately prepared, freshly reviewed operation based on current state, with a duplicate-effect warning. The model cannot acknowledge ambiguity or reuse the old operation ID to execute. No automatic retry button for unknown outcomes.

Operation receipts are product records in existing SQLite, separate from seven-day diagnostic retention: cap 1,000 per Project; automatically prune closed receipts after 30 days, oldest first. Closed means succeeded, verified effect-free failed/cancelled/denied/stale/expired, or unknown with explicit human acknowledgement. Never evict executing, live pending approvals, or unacknowledged unknowns. At capacity, expire eligible preparations and prune eligible closed records before rejecting a new preparation. Offer inspect/reconcile/acknowledge for unknowns and explicit human deletion of closed history with a retention/replay warning, so capacity is recoverable without removing active records. This narrow receipt inspection/recovery control is part of both surfaces, not a history dashboard.

Replay protection after pruning is fail-closed: execute/resume only looks up an existing server-issued receipt and never upserts it. Missing, expired, pruned or terminal effect-free IDs return a non-executing rejection/result; they cannot create an operation. A user must start new preparation and fresh approval. Idempotent result retrieval applies only while the receipt is retained. Migration from the current SQLite schema must preserve sessions, approvals and diagnostics; repeat startup/migration cannot execute effects. Scope review is required if this mechanism cannot meet these invariants without a generalized workflow engine.

### Diagnostics and safety

Reuse V1 request/run/tool/approval events; safe results carry operation ID, outcome, full commit/ref/PR identities where allowed. Reports must explain requested → waiting → executed/denied/unknown and correlation across resume without logging diff contents, credentials, full prompts or raw git stderr. Sanitise errors/remote URLs and exclude token-bearing URLs, sensitive path contents and unbounded hook output. Known broader diagnostic lineage issues remain separate; do not claim absence of events proves no effect. Independently inspect real Git effects and export reports for success and denial/uncertainty.
