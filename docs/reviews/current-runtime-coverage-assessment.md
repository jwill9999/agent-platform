## Material corrections and findings

1. **Critic and completion are excluded from ordinary chat intentionally.** [buildRuntimeGraph](../../apps/api/src/infrastructure/http/v1/chatRouter.ts) passes undefined critic, DoD proposer and checker nodes. Its comment cites internal JSON/error leakage and an additional model call. The route also initializes react mode. Existing API test explicitly verifies no DoD prompts even when `disableEvaluatorNodes` is false. Earlier discussion that default chat may call these evaluators was incorrect for this revision. Library tests and feedback components do not prove runtime activation. This establishes why the inspected chat path emits no critic verdict, not the historical timing of the owner's reported disappearance.
2. **Automatic does not currently exempt the sampled shell write.** Calling the actual command classifier with `touch notes.md` produced approval-required for Ask and Auto, denied for Block. [approvalDecision](../../packages/harness/src/security/bashCommandPolicy.ts) distinguishes Block from all other modes. Tool-level high-risk gating adds a separate approval layer. This is reproduced behavior and a potential mismatch with the UI expectation; changing permission policy requires an explicit decision, not an incidental small fix.
3. **Execution settings are platform-wide.** [settings repository](../../packages/db/src/repositories/settings.ts) loads key/value settings without a project dimension; chat reads `loadSettings(db).executionPolicy`. A preference changed during a test must use disposable app/database state. A persistent per-action/per-project exception is not established by this implementation.
4. **Critic acceptance can mean evaluator failure.** The fallback test named malformed-output actually injects a thrown evaluator. Real default JSON parsing still needs targeted coverage. Completion has different failure behavior. Re-enabling either node is not needed for the first tool-loop baseline and is outside its scope.

## Provider fixture feasibility

The factory accepts a custom URL but the ordinary reasoning node does not forward model-config baseURL. Rather than add that feature, select `provider: ollama` and set `OLLAMA_BASE_URL` to the disposable loopback server's `/v1` endpoint. The [factory](../../packages/model-router/src/providers.ts) reads that environment variable; [provider resolution](../../packages/model-router/src/resolveApiKey.ts) needs no real key. The installed OpenAI provider instead defaults its URL when omitted; do not assume an OpenAI environment URL override works.

The temporary probe made two `/v1/chat/completions` requests. The first returned a streamed function call; the real reasoning node produced the expected tool name and parsed arguments. A manually supplied tool result was then sent back under the same call ID; the second response produced the expected final text. Fetch was restricted to the loopback origin. Result: transport, schema and identity feasibility **passed**. It did not exercise tool execution, LangGraph routing, approval, SQLite, UI, actual Ollama or model quality.

[Probe source and result](harness-provider-fixture-probe.md) preserves the temporary experiment for reproduction. It is not a committed test-suite entry or product implementation.

For Electron, [backendSupervisor](../../apps/desktop/src/main/backendSupervisor.ts) forwards environment into its child process, and the existing [journey launcher](../../apps/desktop/e2e/packaged-vm-command.e2e.ts) controls disposable runtime settings. The future test must remove both whole-node override variables, explicitly select the fixture-backed model/agent, and verify the actual outgoing request rather than assuming environment defaults win over seeded overrides. Full desktop composition remains the first implementation check.
